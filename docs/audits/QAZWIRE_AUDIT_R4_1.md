## 4. Задача 1: чередования (модель реализации)

Проверяемые свойства безопасности — выполнены во всех конфигурациях с разными провайдерами (M-1…M-4, M-6):

| Свойство | Смысл |
| --- | --- |
| `refs_underflow` | Непарный `leave` |
| `wipe_with_outstanding_lease` | Стирание, пока жив seal, пакет в очереди или отправка ключа (эталонный подсчёт по состояниям потоков) |
| `process_on_wiped_provider`, `process_after_key_wipe` | Работа провайдера после стирания |
| `send_after_drain_confirmed` | `wire.send` после того, как `awaitDrained` наблюдал завершение egress |
| `send_with_wiped_key` | Отправка пакета, чей ключ уже стёрт |
| `dup_send`, `dup_ticket` | Повторная отправка guard; повтор билета в поколении |

Финальные свойства (во всех терминальных состояниях):

- после аварии очередь пуста, все шлюзы опустошены и завершены;
- без аварии каждое ротированное поколение стёрто — **нарушается только в M-4** (R41-04).

Deadlock (терминальное состояние с живыми потоками) не найден ни в одной конфигурации.

Достижимые наблюдения (кратчайшие трассы из `sessionlab_model_output.txt`):

## 8. Задача 5: аварийная остановка и ротация

**Аварийная остановка.**
- **A1:** egress закрывается до `Lock` (`:358`).
- **A2:** `closed` и снимок поколений берутся под тем же мьютексом, что и в `rotate` (`:359–360`).
- **A3:** очередь сбрасывается с освобождением Lease (`:362–368`); все поколения закрываются (`:369–371`).
- **A4:** `awaitDrained` сначала ждёт egress (`:389`).

Модель: отправка после подтверждённого опустошения недостижима, финальное свойство «всё опустошено и стёрто» выполнено. Мутанты без шлюза egress, без сброса очереди и без проверки `closed` в `rotate` обнаружены. **VERIFIED.**

**Ротация.** Безопасна: ключ старого поколения жив, пока его пакеты в очереди. Но:
- пакеты в полёте теряются, и `errClosed` возвращается при открытой сессии (R41-03);
- время жизни ротированного поколения не ограничено (R41-04);
- провайдер можно переиспользовать (R41-01);
- сбои стирания ротированного поколения не доходят до владельца (R41-05).

## 9. Ошибки: механизм, тест, минимальное исправление

Тесты — `sessionlab_blackbox/r41_blackbox_test.go` (на неизменённом коде; каждый печатает `CONFIRMED`). Исправления — `sessionlab_fix/session_r41_minimal_fix.patch`, проверка — `sessionlab_fix/r41_fixed_test.go`.

### R41-01 — один объект провайдера для двух поколений или сессий (MEDIUM)

- **Механизм:** `newSession` (`:252–258`) и `rotate` (`:338–353`) не проверяют, что провайдер не используется. `rotate(p_old)` создаёт новое поколение на том же объекте; `old.gate.beginClose()` (`:351`) запускает `finish = p.wipe` (`:161`) — и стирает состояние, которым продолжает пользоваться живое поколение.
- **Трасса (M-5, 10 шагов):** см. §4.
- **Тест:** `TestR41_01_ProviderAliasedAcrossGenerations` — после стирания старого поколения `process()` на «стёртом» провайдере успешен; тот же объект принимает и вторая сессия.
- **Исправление:** реестр объектов провайдера на уровне процесса (`claimProvider` через `sync.Map`): объект может обслуживать ровно одно поколение и никогда не переиспользуется; `errProviderReuse`. Архитектурно (R4 §7.2): провайдер создаёт сам пакет из поглощённого материала. Тест: `TestFix01`.

### R41-02 — значимый провайдер: `wipe()` стирает копию (MEDIUM)

- **Механизм:** `validDependency` (`:240–250`) пропускает значения всех видов, кроме допускающих `nil`. Для значимого типа `newGate(p.wipe)` (`:161`) связывает **копию** получателя: `wipe` обнуляет копию, а состояние в `k.p` остаётся. `awaitDrained` возвращает `nil` — «уничтожение подтверждено», хотя ничего не стёрто.
- **Тест:** `TestR41_02_ValueProviderWipeIsOnACopy` (`material[0] = 0xa5` после успешного `awaitDrained`).
- **Исправление:** `validProvider` требует ненулевой указатель. Получатель `wipe` по указателю `reflect` для неэкспортируемого метода проверить не может — это ещё один довод за конкретный тип провайдера (R4 §7.2). Тест: `TestFix02`.

### R41-03 — ротация теряет пакеты в полёте; `errClosed` при открытой сессии (MEDIUM, доступность)

- **Механизм 1 (4 шага):** `prepare` читает `s.k` под `RLock` и отпускает замок (`:261–267`); `rotate` закрывает это поколение; `seal` получает отказ `enter` (`:187–189`).
- **Механизм 2:** проверка после `process` (`:208`) срабатывает на `closingFlag`, который ставит и плановая ротация (`:351`). Уже обработанный пакет отбрасывается.
- **Последствие:** в обоих случаях — `errClosed`, то же значение (`:25`), что и при остановке сессии. Отдельного бита «отбрасывать вывод» (R4 I-1, R4-KLM-10) нет.
- **Тест:** `TestR41_03_RotationDropsInFlightPacket`.
- **Исправление:** `discardFlag` ставят только авария и `poison` (`beginDiscard`), а проверка после `process` смотрит на него. Плановая ротация сохраняет вывод — пакет уходит на ротированном поколении. `prepare` при `errClosed` и открытой сессии один раз повторяет попытку с текущим поколением. Тесты: `TestFix03`, `TestFix03b`.

### R41-04 — забытый пакет навсегда удерживает ротированный ключ; поколения не удаляются (MEDIUM)

- **Механизм:** Lease пакета держит ключ (`:217–220`), а освобождают его только `dispatch`, `discard` или авария. В `rotate` (`:350`) поколения только добавляются; срока жизни у ротированного поколения нет.
- **Тест:** `TestR41_04_LeakedPacketPinsRetiredKey` — после 1000 ротаций первое поколение не стёрто, `len(s.keys) = 1001`.
- **Модель:** M-4 — нарушение финального свойства.
- **Исправление:** как у wireguard-go с «предыдущей» парой ключей — пакеты в очереди может держать **только одно** ротированное поколение. При следующей ротации пакеты более старых поколений сбрасываются через `discard`, полностью завершённые поколения удаляются из `s.keys`. Тест: `TestFix04` (первое поколение стёрто, `len(s.keys) ≤ 3`).

### R41-05 — сбои не доходят до владельца (MEDIUM)

- **Механизм:** `failedFlag` ротированного поколения ставится в горутине finish (`:107–112`), но никто его не наблюдает до `awaitDrained`, а тот допустим только после аварии (`:383–386`). `poisonFlag` (`:19`) только записывается (`:127`).
- **Тесты:** `TestR41_05_RotatedKeyWipeFailureIsSilent` (после сбоя стирания сессия обслуживает ещё 3 пакета), `TestR41_05b_PoisonNotSurfacedByAwaitDrained`.
- **Исправление:** у шлюза поколения есть `onFail = s.beginEmergency`. Он вызывается в отдельной горутине при panic `finish` — по R4 §7.7 WIPE_FAILED означает обязательную эскалацию. Добавлен `faultState()`, который сообщает POISONED и WIPE_FAILED. Семантика `awaitDrained` не меняется, поэтому тесты владельца остаются в силе. Тесты: `TestFix05`, `TestFix05b`.

### R41-06 — «стирание не подтверждено» неотличимо от «операция идёт» (LOW)

- **Механизм:** `gate.await` по дедлайну всегда возвращает `errDeadline` (`:147–148`), хотя состояния разные: `0xc000000000000000` (refs = 0, стирание начато) и `0x8000000000000001` (refs = 1).
- **Тест:** `TestR41_06_DeadlineDoesNotDistinguishWipeHang`.
- **Исправление:** при установленном `finishedFlag` возвращается `errWipeUnconfirmed`, оборачивающий `errDeadline` (`errors.Is` с `errDeadline` сохраняется — тест владельца `TestWipeHangNeverReportsSuccess` проходит). Тест: `TestFix06`.

### R41-07 — владение буферами (LOW–MEDIUM)

- **Механизм:** `prepare` возвращает `pkt` с тем же `data`, что лежит в `pending` (`:284–286`). `discard`, авария и сжигание обнуляют этот массив (`:281`, `:299`, `:364`) уже после передачи вызывающему. `seal` ставит в очередь `result` без копии (`:207`, `:220`): если обработчик пишет «на месте», в очереди оказывается буфер вызывающего.
- **Тесты:** `TestR41_07a_ReturnedRecordMutatedAfterHandOff` (запись вызывающего обнулена после `beginEmergency`); `TestR41_07b_InPlaceOutputAliasesCallerBuffer` (запечатано `AAAA`, отправлено `BBBB`; `discard` обнулил буфер вызывающего).
- **Исправление:** вызывающему возвращается дескриптор без `data` — буфер очереди принадлежит только сессии. Выход, начинающийся с того же адреса, что вход, копируется. Полная проверка перекрытия требует `unsafe` и остаётся на уровне контракта провайдера (R4 §7.7). Тест: `TestFix07`.

### R41-08 — детектор гонок не видит `clear()` (INFO, влияет на доказательную базу)

На Go 1.24.7 гонка между `clear(b)` и чтением `b` в другой горутине под `-race` не сообщается, а та же гонка с записью `b[0] = 0` сообщается. Вероятная причина — `clear` превращается в вызов runtime (`memclr`), который не инструментируется; это гипотеза аудитора, известный тикет не найден. Следствие: PASS под `-race`, в том числе `-count=100` у владельца, не покрывает гонки на очистке буферов (R41-07). Демонстрация — `racechk/`.

## 11. Минимальный патч

`sessionlab_fix/session_r41_minimal_fix.patch` меняет 120 строк `session.go`. Каждое изменение помечено `FIX R41-NN`:

| Исправление | Суть |
| --- | --- |
| R41-01 | `claimProvider` (реестр `sync.Map`), `errProviderReuse` |
| R41-02 | `validProvider` — только ненулевой указатель |
| R41-03 | `discardFlag` / `beginDiscard` для аварии и `poison`; проверка после `process` по `discardFlag`; одна повторная попытка в `prepare` |

| R41-05 | `gate.onFail` → `beginEmergency` при panic `finish`; `faultState()` |
| R41-06 | `errWipeUnconfirmed` (оборачивает `errDeadline`) |
| R41-07 | `prepare` не возвращает `data`; копия выхода, совмещённого со входом |

Проверка на исправленной копии: 9 тестов исправлений, стресс и **все 17 тестов владельца без изменений** — PASS (`-race`, `-count=10`). Ограничения патча:
- реестр провайдеров растёт с числом поколений — для лаборатории это приемлемо, для эксплуатации нужен конкретный тип провайдера;
- `onFail` переводит сессию в аварию асинхронно;
- модель исправленного кода не строилась (PENDING);
- поведение ротации изменено — пакеты в полёте сохраняются, а это решение владельца.
