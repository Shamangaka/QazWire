## 1. Заключение (Executive conclusion)

1. **Безопасная интеграция Qalqan в WireGuard возможна только как новый, несовместимый протокол**, а не как «замена шифра». В wireguard-go размер тега, длина nonce, форматы сообщений, начальные константы транскрипта и выбор AEAD жёстко зашиты в код (см. §2). Любая замена порождает другой протокол с собственным идентификатором, собственными ключами и собственным доказательством безопасности. Это подтверждает вывод `PROTOCOL_BOUNDARY_V0_1.md` и уточняет его.
2. **СТ РК 4009-2025 определяет только блочный шифр** (параметры — §3). Стандарт не определяет ни режим аутентифицированного шифрования, ни алгоритм имитовставки: §1.1 отсылает и шифрование «в различных режимах», и выработку имитовставки к СТ РК ISO/IEC 10116, который определяет только режимы шифрования (ECB/CBC/CFB/OFB/CTR) и имитовставку не определяет. **Конструкция AE для VPN должна заимствоваться из СТ РК ISO/IEC 19772 / 9797-1 или проектироваться как исследовательская** — это нормативный пробел (QW-R1-F02).
3. **Буквальное применение механизма 5 (Encrypt-then-MAC) СТ РК ISO/IEC 19772-2013 небезопасно для VPN**: MAC вычисляется только над шифртекстом C′, начальное значение S и заголовок пакета не аутентифицируются (§10.4–10.5 стандарта). Эта уязвимость конструкции ISO/IEC 19772:2009 опубликована (Namprempre–Rogaway–Shrimpton, EUROCRYPT 2014). Допустим только профилированный вариант, где MAC покрывает заголовок, счётчик и шифртекст (QW-R1-F03).
4. **Рекомендуемая для исследовательской реализации конструкция (CONDITIONAL):** вариант **A** — Qalqan с блоком 256 бит и ключом 256 бит в режиме CTR (ISO/IEC 10116 §10) + имитовставка Qalqan-EMAC (ISO/IEC 9797-1, алгоритм MAC 2, метод дополнения 2), композиция Encrypt-then-MAC в форме «N2» (MAC над заголовком, счётчиком и шифртекстом), три независимых ключа на направление, тег 256 бит. Обоснование — §5. Допустимая альтернатива для профилей с длиной тега ≤128 бит — вариант **B** (Qalqan-128 CTR + CMAC-128).
5. **Защита реального трафика любым вариантом с Qalqan — BLOCKED** до закрытия блокирующих рисков §9: отсутствует найденный публичный независимый криптоанализ стандартизованной версии Qalqan 2025 года (опубликованный анализ относится к более ранней версии v1 с другими S-блоком и линейным слоем); стратегия constant-time реализации не определена; не решены нормативные вопросы §4.4 и §5.5.7/§5.6.7 СТ РК 1073-2025.
6. **Handshake национальными алгоритмами — BLOCKED** (нет найденного в корпусе проекта национального стандарта согласования ключей; см. `QAZWIRE_ST_RK_APPLICABILITY_R1.md`). Профиль v0.1 сохраняет X25519/BLAKE2s/ChaCha20-Poly1305 в handshake как «гибридный исследовательский». Следствие: даже по длинам параметров handshake не проходит пороги L3/L4 (X25519 — 255-битный ключ при пороге 320; BLAKE2s — 256 бит при пороге 320; теги 128 бит при пороге 160). **Никакой уровень L1–L4 не заявляется.**

**Решение R1:** архитектура варианта A допускается к реализации в изолированной исследовательской ветке после выполнения входных условий из `QAZWIRE_PROTOCOL_SPEC_R1.md` §0. Решение «пригодно для защиты информации» — **BLOCKED**.

### 2.5 KDF

WireGuard использует HKDF (RFC 5869) с HMAC-BLAKE2s, без поля info; `KDF1/2/3` (`noise-helpers.go:43–63`) выдают 1–3 блока по 32 байта. Транспортные ключи: `KDF2(sendKey, recvKey, chainKey, nil)` (`noise-protocol.go:634–647`).
**v0.1:** сохраняется до получения ck; затем каждый направленный 32-байтовый ключ расширяется в три ключа Qalqan с явными метками (HKDF-Expand с info; см. спецификацию §7). Требование §5.1.4 СТ РК 1073-2025 (один ключ — один алгоритм — одна цель) выполняется на уровне архитектуры ключей.

### 2.6 Аутентификация участников

Взаимная аутентификация обеспечивается DH-операциями со static-ключами (es, ss, se) и PSK (psk2), подтверждением через AEAD-теги (`:366`, `:398`, `:581`) и первым транспортным пакетом (подтверждение ключа на транспортном уровне). Поиск пира — по расшифрованному static-ключу (`:374`). Формальные анализы: Lipp–Blanchet–Bhargavan (CryptoVerif, 2019), Donenfeld–Milner (Tamarin), Dowling–Paterson (2018) — см. §11. **v0.1:** логика сохраняется; меняются только доменные константы, поэтому структура доказательств переносится при условии, что транспортный AEAD заменён на конструкцию с теми же свойствами (IND-CPA + INT-CTXT) — это **требует отдельного доказательства** (см. Threat Model §5).

### 2.7 Формирование транспортных ключей

`BeginSymmetricSession` (`noise-protocol.go:621–708`): направленные ключи, обнуление ck/h/эфемерного ключа (`:655–657`), создание AEAD-объектов (`:663–664`), обнуление массивов `sendKey/recvKey` (`:666–667`), ротация `previous/current/next` (`:682–705`).
Наблюдение: `chacha20poly1305.New` копирует ключ внутрь объекта; при удалении пары (`keypair.go:48–52` `DeleteKeypair` — только удаление индекса) ключевой материал **не стирается** и остаётся в куче до сборки мусора. Комментарий разработчиков в `keypair.go:17–22` прямо признаёт это. См. F09.

### 2.8 Обновление ключей

`constants.go:15–26`: `RekeyAfterMessages = 2^60`, `RejectAfterMessages = 2^64 − 2^13 − 1`, `RekeyAfterTime = 120 c`, `RejectAfterTime = 180 c`. Проверки: `send.go:195–204` (`keepKeyFreshSending`), `send.go:344` и `:356–358` (жёсткий отказ), `receive.go:164` (истечение пары на приёме), `timers.go:126–129` (стирание всех ключей через 3×RejectAfterTime).
**v0.1:** лимиты становятся параметрами профиля. Для 128-битного блока лимит по сообщениям обязан учитывать границу «дня рождения» (F07).

### 2.9 Защита от повторов

Транспорт: RFC 6479, окно `(128 − 1) × 64 = 8128` значений (`replay/replay.go:11–18`), `ValidateCounter` отвергает счётчик ≥ лимита (`:37–40`); вызывается **после** успешной аутентификации (`receive.go:453`, пакеты с неудачным `Open` отброшены ранее `:449–451` → `elem.packet == nil`). Handshake: монотонная TAI64N-метка и ограничение частоты (`noise-protocol.go:405–417`); метка округляется маской (`tai64n/tai64n.go:17`, `:25`). **v0.1:** без изменений алгоритма; порядок «аутентификация → окно» обязателен.

### 2.10 Управление nonce

Транспорт: 64-битный счётчик на пару ключей, атомарное приращение (`send.go:356`), запись в заголовок little-endian (`:457`) и в nonce ChaCha20-Poly1305 (байты 4..11, `:465`). Handshake: нулевой nonce при однократных ключах. Cookie: случайный 192-битный nonce (`cookie.go:159`).
**v0.1:** счётчик пакета сохраняется; блок-счётчик CTR формируется из него детерминированно и не пересекается между пакетами (спецификация §8.2). Параметр `NoiseNonce` (`noise-types.go:24`) — комментарий «padded to 12-bytes» становится неверным для нового профиля.

### 2.11 Форматы сообщений

`noise-protocol.go:56–117`: типы 1–4 (`:57–60`) в 32-битном little-endian поле с тремя нулевыми байтами (`:79–83`); фиксированные размеры 148/92/64 и заголовок транспорта 16 байт (`:64–71`); смещения `:73–77`. Разбор по точной длине (`:121–209`) и минимальной длине на приёме (`receive.go:130`, `:147`, `:191`).
**v0.1:** новые коды типов и байт профиля; размеры handshake в v0.1 не меняются; транспорт +16 байт к накладным расходам (тег 32 вместо 16). Детали — спецификация §4.

### 2.12 Защита от downgrade

WireGuard **не криптоагилен**: нет согласования алгоритмов, поэтому нет и поверхности для downgrade внутри протокола. Единственная «версия» — `protocol_version=1` в UAPI (`uapi.go:395–398`). Риск появляется именно при введении профилей. **v0.1:** профиль неизменяем на уровне устройства, нет согласования, нет fallback; профиль входит в имя конструкции, в коды типов и в метки KDF; при сбое самопроверок устройство не запускается (fail-closed).

### 3.3 Анализ, выполненный аудитором (C1–C6)

Инструмент `docs/audits/tools/qalqan_component_analysis.py` читает локальную лицензионную копию стандарта (после `pdftotext -layout`) и **не содержит** данных стандарта. Запуск 2026-11-02, Python 3, время ≈35 с. Полный вывод:

```
C1 bijective=True inverse_table_ok=True fixed_points=0
C2 differential_uniformity=4 max_abs_walsh=32 nonlinearity=112 algebraic_degree=[7,7]
C3 linear KAT blen=128 PASS
C3 linear KAT blen=256 PASS
C3 linear KAT blen=512 PASS
C3 linear KAT blen=128 PASS
C3 linear KAT blen=256 PASS
C3 linear KAT blen=512 PASS
C4 blen=128 byte branch number: differential=5 (witness in=(0, 10) out=(0, 10, 12)); linear=5 (witness in=(0,) out=(0, 4, 10, 14))
C5 blen=256 upper bound from 1-active-byte inputs: 22 (byte 0 value 0x01)
C5 blen=512 upper bound from 1-active-byte inputs: 27 (byte 0 value 0x01)
C6 blen=256 round keys 0..2 equal concatenated blen=128 round keys: [True, True, True]
C6 blen=512 round keys 0..2 equal concatenated blen=128 round keys: [True, True, True]
```

Интерпретация:

- **C1–C2:** S-блок биективен, табл. 3 — его обращение, неподвижных точек нет; разностная равномерность 4, нелинейность 112, алгебраическая степень 7 у всех компонент. Это совпадает с характеристиками S-блока AES и является **необходимым, но не достаточным** условием стойкости.
- **C3:** реализация формулы (1) аудитором (последовательное обновление слов, слова little-endian) воспроизводит все шесть векторов линейного слоя Прил. А. Интерпретация §6.2 подтверждена.
- **C4:** точное байтовое число ветвления L для Blen=128 равно **5** (и для разностей, и для линейных масок, через L^T). Это заметно ниже максимально возможного для 16-байтового слоя (17). Грубая оценка «≥5 активных S-блоков на каждые 2 раунда» при максимальной вероятности разностного перехода S-блока 2^−6 даёт для 15 нелинейных слоёв (Klen=256) порядка ≥35 активных S-блоков на характеристику — это **грубая эвристика по характеристикам, а не доказательство стойкости** (не учитываются кластеризация дифференциалов, связанные ключи, алгебраические, интегральные и иные атаки из §4.5 СТ РК 1073-2025).
- **C5:** для Blen=256/512 точное число ветвления не вычислено (комбинаторно дорого); получены только верхние оценки 22/27 по однобайтовым входам → **PENDING** (MILP/SAT-анализ).
- **C6:** подтверждено QW-R1-F05 на обязательных проверочных данных.

### 3.4 Публичный криптоанализ

- Яковлев, Столович (КПИ, 2022) показали для **первой версии** Qalqan (2021) число ветвления линейного слоя 3 и большое количество неподвижных точек, а также многораундовые характеристики для модифицированной версии; авторы рекомендуют пересмотреть заявленную стойкость. Описание Qalqan в публикации Seilova et al. (CEUR-WS Vol-3187) содержит **другой** S-блок (иные значения S(00), S(01), S(ff), чем в табл. 1 СТ РК 4009-2025) и линейный слой на побайтовых сложениях по mod 256 вместо XOR циклических сдвигов слов (§6.2 стандарта), т.е. стандартизованная в 2025 г. версия — **иной** дизайн, и выводы о v1 на неё напрямую не переносятся (как и не опровергаются).
- Работы по атакам сбоев (DFA, КПИ, 2024) также относятся к модифицированной/ранней версии.
- Публичного независимого криптоанализа версии СТ РК 4009-2025 в ходе R1 **не найдено** (поиск 2026-11-02). Это не доказывает его отсутствие; требуется запрос разработчику стандарта и обзор закрытых/русскоязычных публикаций. Статус: **BLOCKED** для защиты реальных данных.

Для Blen=256 в Прил. А есть векторы зашифрования при Klen=256. Независимые ключи шифрования и имитовставки устраняют вопрос о §5.1.4, который возникает у однопроходных/однокле́вых режимов (C, D, E и ChaCha20-Poly1305). Цена — производительность и отсутствие публичного анализа именно 256-битного варианта. **Это не изобретение новой криптографической конструкции**: CTR, EMAC и композиция N2 — известные конструкции с опубликованными доказательствами; новым является только профилирование входа MAC относительно 19772-2013 мех. 5, которое помечено как требующее нормативного согласования и независимой проверки.

## 6. Целевая архитектура интеграции

```
                       ┌────────────── QazWire device (профиль неизменяем) ──────────────┐
UAPI/конфиг ──► Profile registry ──► Handshake (Noise IKpsk2, домен QazWire) ──► ck
                                         │                                         │
                                         ▼                                         ▼
                                   Cookie/MAC1/MAC2 (метки QazWire)        TransportKeySchedule
                                                                           (HKDF-Expand с метками)
                                                                                   │
                                     ┌─────────────────────────────────────────────┘
                                     ▼
                         TransportSuite (интерфейс, fail-closed)
                           ├── Seal(hdr, ctr, pt) → ct‖tag   (CTR → EMAC)
                           ├── Open(hdr, ctr, ct‖tag) → pt | ErrAuth (EMAC verify → CTR)
                           ├── Overhead(), Limits()
                           └── Destroy() (refcount, после — только ошибки)
                                     │
                     ┌───────────────┴────────────────┐
                     ▼                                ▼
             Go-провайдер Qalqan              FFI-провайдер QazInfraCrypto (Rust)
             (исследовательский)              (будущая оцениваемая граница)
                     └────── дифференциальные тесты ──┘   + референс Прил. Б (UBSan)
```

Принципы: (1) профиль выбирается при создании устройства и не меняется; (2) стандартный WireGuard остаётся только в `master` и в отдельной сборке — нет смешения пиров разных протоколов в одном устройстве; (3) нет согласования и fallback; (4) интерфейс транспорта не принимает nonce от вызывающего — только счётчик пары ключей; (5) ошибки — без различимых сообщений, без выдачи открытого текста.
