### Разбор R42-01

`processor` — пакетно-частный интерфейс, а не конкретный закрытый провайдер. Метод `claim()` реализован в **каждом экземпляре** `providerClaim`, не в материале. Два различных экземпляра с одним `shared` проходят проверку даже без копирования atomics. Это не исправляется глобальным `sync.Map`, который удерживал бы секретные объекты навсегда. Для production необходим единственный module-private constructor, который **поглощает** уникальный secret owner, запрещает aliasing/копирование и не принимает сторонние интерфейсы. Одноразовый флаг годится лишь как вторичная защита. Отдельно нужны проверки zeroization, FFI и компиляторных копий.

### Разбор R42-02

`live := s.keys[:0]` фильтрует `len`, но не обнуляет записи базового массива за новым `len`. Рецепт минимального изменения (только для просмотра; **не применён к feature-ветке**): после завершения цикла фильтрации и до `append(live,fresh)` выполнить `clear(s.keys[:cap(s.keys)][len(live):])` под `session.mu`. Патч: `docs/audits/tools/_r4_2_harness/patches/r42_02_clear_retired_capacity.patch`. **Изолированная временная копия с патчем прошла этот негативный тест с `-race` в CI #41591986302 и #41592174563; патч не применён к PR #13.** Независимое ревью concurrent ownership/GC всё ещё требуется. `clear()` здесь касается указателей на объекты и не должен выдаваться за гарантированное стирание материала.

## 3. Независимая ограниченная модель M1.5.2

`docs/audits/tools/_r4_2_harness/m152_model.py` — независимая **ручная абстракция**, не автоматически извлечённый Go-код. Состояния сериализованы в immutable tuples; BFS перечисляет возможные переходы и сохраняет кратчайшую трассу контрпримера.

Границы: **один** worker (prepare → provider → queue → dispatch/discard, одна повторная попытка), **две последовательные плановые ротации**, максимум **три поколения**, один ticket на поколение, один поток аварии (две фазы), отдельный egress gate и асинхронное успешное wipe. Секция `session.mu` атомарна; CAS моделируется на уровне успешного перехода. **Не моделируются** два одновременных worker, зависание/panic/error провайдера, реальные buffers/IO, scheduling fairness, реальные ключи/nonce, все fallback-пути `go test` и физическая память.

Локальный запуск Python 3 и GitHub Actions #41591343263:

| Вариант | Состояний | Исход |
| --- | ---: | --- |
| Исходная модель | **1 833** | Не обнаружены нарушения *смоделированных* свойств |
| Мутант: ранний release до send | **1 240** (до контрпримера) | Найдена отправка после wipe |
| Мутант: обход egress gate | **1 180** (до контрпримера) | Найдена отправка после подтверждения drain |

3/3 мутаций обнаружены; для составного grandparent-мутанта одновременно отключены fence+age-check, что НЕ доказывает чувствительность модели к каждой защите по отдельности. **Это недостаточно для полной T-KLM-27; статус PARTIAL.** Предыдущая модель R4.1 охватывала больше worker, но не исходники M1.5.2, поэтому её заключение напрямую переносить нельзя.

## 4. Ротация и соответствие реальному WireGuard

**Решение №1: позволять уже начатой операции предыдущего поколения завершить и отправить пакет.** Условный **GO для синтетического lab**. Перед применением в VPN необходимо определить, какое поколение принимающая сторона ещё может аутентифицировать; использовать per-packet receiver index/key identity и счётчик под ключом; защитить nonce и replay-состояния на смене эпох. Обычный WireGuard в `device/send.go` сохраняет `elem.keypair` на пакет и записывает `remoteIndex` в заголовок; `device/receive.go` выбирает ключ по receiver index. Synthetic `wire.send(ticket, data)` этой идентичности не несёт.

**Решение №2: при второй ротации отбрасывать очередь поколений старше предыдущего.** Условный **GO для синтетического lab** с явным признанием неизбежной потери пакетов. Это не обеспечивает автоматически безопасный приём на удалённой стороне, не задаёт ограничение числа зависших поколений и не снимает требования retransmission/replay/epoch metadata. Точный протокольный контракт должен быть отдельно сформулирован и проверен в netns.
