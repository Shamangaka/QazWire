## 1. Архитектура компонентов

```
┌──────────────────────────────── qazwire-go (отдельный бинарник, build tag qazwire_exp) ────────────────────────────────┐
│ Config/UAPI ──► ProfileRegistry (неизменяемый ProfileID на устройство, самотест при создании; при ошибке — отказ)       │
│                     │                                                                                                  │
│                     ├──► HandshakeEngine  (Noise IKpsk2 / X25519 / ChaChaPoly / BLAKE2s; доменные константы профиля)   │
│                     │        └──► CookieEngine (MAC1/MAC2/cookie — метки профиля)                                      │
│                     ├──► TransportKeySchedule (KDF2 → HKDF-Expand с метками → K_e, K_m, K_m′ на направление)           │
│                     └──► TransportSuite ─┬─► QalqanProvider (Go | FFI→QazInfraCrypto)                                  │
│                                          ├─► CTR (ISO/IEC 10116 §10)                                                   │
│                                          └─► EMAC (9797-1 MAC 2) | CMAC (9797-1 MAC 5, только Blen=128)                 │
│ Send path: TUN → padding → Seal(H, P) → UDP           Receive path: UDP → parse H → lookup → Open(H, C‖T) → replay → TUN│
└────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
   master (wireguard-go upstream) — отдельная сборка, код QazWire в неё не входит.
```

Правила изоляции:

1. Код QazWire MUST находиться только в экспериментальных ветках и MUST компилироваться только с build tag `qazwire_exp`. Сборка `master` MUST оставаться побайтно эквивалентной по поведению upstream (T-DIFF-03).
2. Одно устройство MUST обслуживать ровно один профиль; смешение пиров WG и QazWire или пиров разных профилей в одном устройстве MUST NOT поддерживаться.
3. Протокол MUST NOT содержать согласования алгоритмов, полей «предлагаемых наборов» или fallback. Любое несовпадение профиля приводит к тихому отбрасыванию.
4. При ошибке самотеста или недоступности провайдера устройство MUST NOT создаваться; переход на ChaCha20-Poly1305 для транспорта MUST NOT происходить.
5. Операционно (не как мера безопасности): имя бинарника `qazwire-go`, порт по умолчанию отличен от 51820 (TBD), явная индикация режима «EXPERIMENTAL QazWire, profile=…» в логах и UAPI (§5.3.8 СТ РК 1073-2025).

## 2. Протокольные профили

| ProfileID | Имя | Handshake | Транспорт | Тег | Статус |
| --- | --- | --- | --- | --- | --- |
| 0x00 | — | — | — | — | Недопустимо (MUST отвергаться) |
| 0x01 | `QWX1-Q256EM` | Noise IKpsk2, X25519, ChaCha20-Poly1305, BLAKE2s (гибридный, международные алгоритмы) | Qalqan Blen=256, Klen=256: CTR + EMAC (MAC 2, доп. 2), EtM-N2 | 256 бит | **Основной исследовательский дизайн** (CONDITIONAL); реализация в транспорте **BLOCKED** (BR-01, BR-02, BR-10) |
| 0x02 | `QWX1-Q128CM` | как 0x01 | Qalqan Blen=128, Klen=256: CTR + CMAC (MAC 5, доп. 4), EtM-N2 | 128 бит | **Исследовательская альтернатива** (R2: не «L2-профиль»); обязательны блочные лимиты и лимит целостности §11; BLOCKED как A |
| 0x03–0x7F | — | — | — | — | Зарезервировано (MUST отвергаться) |
| 0x80–0xFF | `QWX2-*` (национальный handshake) | **BLOCKED**: нет выбранного национального механизма согласования ключей | — | — | **BLOCKED** |

Профиль `QWX0` («стандартный WireGuard») существует **только** как эталон для дифференциальных тестов и бенчмарков и в QazWire-сборку не входит.

## 3. Версионирование и идентификация

### 3.1 Строки идентификации

| Константа | Значение (байты ASCII, без завершающего нуля) | Назначение |
| --- | --- | --- |
| `ProtocolIdentifier` (UAPI) | `qazwire-exp-0.1` | Единственное допустимое значение ключа UAPI `protocol_version` у QazWire-устройства; значение `1` MUST отвергаться |
| `Construction(p)` | `QazWire-Exp-0.1/` ‖ `ProfileName(p)` ‖ `/Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s` | Хешируется в ck0 |
| `Prologue(p)` | `QazWire v0.1 experimental research-only profile=` ‖ `ProfileName(p)` | Хешируется в h0 |
| `LabelMAC1(p)` | `qw1mac1` ‖ p (8 байт) | Ключ MAC1 = BLAKE2s(LabelMAC1 ‖ S_pub(responder)) |
| `LabelCookie(p)` | `qw1cook` ‖ p (8 байт) | Ключ шифрования cookie = BLAKE2s(LabelCookie ‖ S_pub(responder)) |

Значения строк — **PENDING** (финализируются на G0), но их структура (профиль внутри строки) — MUST.

### 3.2 Начальные значения транскрипта

```
ck0 = BLAKE2s-256( Construction(p) )
h0  = BLAKE2s-256( ck0 ‖ Prologue(p) )
```

**Обоснование (QW-R1-F10).** В wireguard-go ключ цепочки зависит от `NoiseConstruction` и DH-выходов, но не от prologue (`device/noise-protocol.go:265–268`, `:280–281`, `:294`, `:303–308`). Изменение только prologue оставило бы ck и транспортные мастер-ключи **идентичными** WireGuard при одинаковых DH-входах. Поэтому профиль MUST входить в `Construction(p)`. ck0/h0 MUST вычисляться на устройство при создании (не глобальные переменные пакета).

### 3.3 Поле типа

Первые 4 байта каждого сообщения:

| Байт | Значение |
| --- | --- |
| 0 | Тип: 0x11 initiation, 0x12 response, 0x13 cookie reply, 0x14 transport (значения 0x01–0x04 WireGuard MUST отвергаться) |
| 1 | ProfileID; MUST совпадать с профилем устройства |
| 2–3 | 0x00 0x00; любое иное значение — отбрасывание |

Связывание профиля с безопасностью обеспечивается **криптографически** (ck0, h0, метки MAC1/cookie, метки KDF); поле типа — ранний фильтр и защита от путаницы, а не механизм безопасности.

## 4. Форматы сообщений

Все многобайтовые целые — little-endian (как в WireGuard), если не указано иное.

### 4.1 Handshake Initiation (148 байт; layout совпадает с WireGuard)

| Смещение | Длина | Поле |
| --- | --- | --- |
| 0 | 4 | Тип/профиль (§3.3), байт 0 = 0x11 |
| 4 | 4 | sender index |
| 8 | 32 | ephemeral public (X25519) |
| 40 | 48 | AEAD(static public) — 32 + тег 16 |
| 88 | 28 | AEAD(TAI64N) — 12 + тег 16 |
| 116 | 16 | MAC1 (BLAKE2s-128, ключ от `LabelMAC1(p)`) |
| 132 | 16 | MAC2 (cookie) |

### 4.2 Handshake Response (92 байта)

| Смещение | Длина | Поле |
| --- | --- | --- |
| 0 | 4 | Тип/профиль, байт 0 = 0x12 |
| 4 | 4 | sender index |
| 8 | 4 | receiver index |
| 12 | 32 | ephemeral public |
| 44 | 16 | AEAD(ε) |
| 60 | 16 | MAC1 |
| 76 | 16 | MAC2 |

### 4.3 Cookie Reply (64 байта)

| Смещение | Длина | Поле |
| --- | --- | --- |
| 0 | 4 | Тип/профиль, байт 0 = 0x13 |
| 4 | 4 | receiver index |
| 8 | 24 | nonce (случайный, XChaCha20-Poly1305) |
| 32 | 32 | XAEAD(cookie) — 16 + тег 16 |

### 4.4 Transport Data

| Смещение | Длина | Поле |
| --- | --- | --- |
| 0 | 4 | Тип/профиль, байт 0 = 0x14 |
| 4 | 4 | receiver index |
| 8 | 8 | counter c (uint64 LE) |
| 16 | L | C — шифртекст CTR дополненного открытого текста P′, L = len(P′) ≥ 0 |
| 16 + L | t/8 | T — имитовставка (32 байта для 0x01; 16 байт для 0x02) |

Минимальный размер: 48 байт (0x01), 32 байта (0x02). Заголовок H = байты 0..15.
Накладные расходы относительно WG: +16 байт для 0x01 → `DefaultMTU` QazWire для 0x01 MUST быть ≤ 1404 при 1420 у WG (`device/tun.go:14`); для 0x02 — без изменения.

## 5. Криптографические интерфейсы

> **R2:** интерфейс ниже — ревизия R1. Нормативной для будущей реализации считается модель KLM из `QAZWIRE_KEY_LIFECYCLE_R2.md` §4–§6: операции только через Lease, счётчик — только через одноразовый `CounterTicket`, состояние и счётчик ссылок в одном атомарном слове, учёт σ_e/σ_tag/σ_ver/q_v внутри ключевого объекта. Требования 1–7 ниже сохраняются.

Эскиз (Go), не реализация:

```go
type ProfileID uint8

// TransportSuite — неизменяемое описание профиля.
type TransportSuite interface {
    ID() ProfileID
    TagSize() int                 // 32 или 16
    Limits() TransportLimits      // §11
    // NewKeys выводит ключи направления из 32-байтового мастер-ключа (§7) и
    // обнуляет master. Ошибка — если провайдер не прошёл самотест или ключи вырождены.
    NewKeys(dir Direction, master *[32]byte) (TransportKeys, error)
    SelfTest() error              // KAT Прил. А + векторы режимов; вызывается при создании устройства
}

type TransportKeys interface {
    // Seal: счётчик берётся ТОЛЬКО из header[8:16]; nonce извне не принимается.
    Seal(dst []byte, header *[16]byte, plaintext []byte) ([]byte, error)
    // Open: проверяет T до любого расшифрования; при ошибке возвращает (nil, ErrAuth)
    // и не записывает открытый текст в dst.
    Open(dst []byte, header *[16]byte, ciphertextAndTag []byte) ([]byte, error)
    // Destroy: best-effort затирание K_e, K_m, K_m′ и раундовых ключей после
    // освобождения последней ссылки; после вызова Seal/Open MUST возвращать ошибку.
    Destroy()
}
```

Требования:

1. **Единый источник счётчика.** Счётчик для CTR MUST извлекаться из аутентифицируемого заголовка, а не передаваться отдельно (устраняет класс ошибок «nonce ≠ аутентифицированный счётчик», ср. NRS 2014).
2. **Fail-closed.** Любая ошибка провайдера → ошибка вызова → отбрасывание пакета. Провайдер MUST NOT паниковать на любых входных данных.
3. **Verify-then-decrypt.** `Open` MUST вычислить и сравнить тег (постоянное время, полная длина) до CTR.
4. **Без усечения.** Длина тега фиксирована профилем; укороченные теги MUST отвергаться.
5. **Подсчёт ссылок.** Пара ключей MUST удерживаться рабочими потоками через счётчик ссылок; `Destroy()` выполняет затирание только после освобождения последней ссылки; флаг «уничтожен» проверяется атомарно в `Seal/Open` (устраняет гонку QW-R1-F09).
6. **Constant-time.** S-блок, развёртывание ключа, сложение mod 2^Blen MUST реализовываться без зависящих от секрета ветвлений и обращений к памяти (метод — G2, TBD).
7. **Отсутствие экспорта.** Интерфейс MUST NOT предоставлять получение сырых ключей; `String()/Format` MUST NOT печатать секреты.

## 6. Обработка handshake

Алгоритм идентичен WireGuard (`CreateMessageInitiation`, `ConsumeMessageInitiation`, `CreateMessageResponse`, `ConsumeMessageResponse` в `device/noise-protocol.go:270–616`) со следующими изменениями:

1. Начальные ck0/h0 — §3.2 (вместо `InitialChainKey/InitialHash`).
2. Проверка типа (`:346`, `:513`) — по §3.3, включая байт профиля и резервные байты.
3. MAC1/MAC2/cookie — метки §3.1.
4. Static-ключи X25519 устройства и пиров QazWire MUST быть отдельными от ключей WireGuard и от ключей другого профиля (§5.1.4 СТ РК 1073-2025; защита от межпротокольных атак). Реализация SHOULD хранить их в отдельных полях конфигурации (§10).
5. PSK MUST быть ненулевым для профилей 0x01/0x02 (гибридная защита и требование REQ-011 QazInfraCrypto «PSK first»). Нулевая PSK → отказ конфигурации.
6. AEAD handshake — ChaCha20-Poly1305 с нулевым nonce, как в WG; каждый ключ handshake MUST использоваться ровно один раз (инвариант `ZeroNonce`, `:231`).
7. Защита от повтора initiation (TAI64N, `:405–417`) и ограничение частоты — без изменений.
8. Общие секреты DH SHOULD обнуляться сразу после `mixKey` во всех путях (в WG — не во всех, QW-R1-F20).

## 7. Формирование сеансовых ключей

После завершения handshake (состояния `handshakeResponseConsumed` / `handshakeResponseCreated`, `:633–651`):

```
(T1, T2) = KDF2(ck, ε)                     -- как в WireGuard
initiator: T_send = T1, T_recv = T2;   responder: T_send = T2, T_recv = T1
dir(i→r) использует T1, dir(r→i) использует T2

для каждого направления d с мастер-ключом T_d:
  K_e  = HKDF-Expand(PRK = T_d, info = Info(p, d, 0x01), L = 32)
  K_m  = HKDF-Expand(PRK = T_d, info = Info(p, d, 0x02), L = 32)
  K_m′ = HKDF-Expand(PRK = T_d, info = Info(p, d, 0x03), L = 32)    -- только профиль 0x01
  обнулить T_d

Info(p, d, u) = "qazwire-exp-0.1" ‖ 0x00 ‖ p ‖ d ‖ u               -- 19 байт, фиксированная длина
  d: 0x01 = i→r, 0x02 = r→i;   u: 0x01 = Qalqan-CTR, 0x02 = MAC key K, 0x03 = EMAC key K′
HKDF-Expand с HMAC-BLAKE2s (RFC 5869 §2.3); при L = 32 = HashLen: OKM = HMAC(T_d, info ‖ 0x01)
```

Требования:

- Каждый ключ привязан к одному алгоритму и одной цели (§5.1.4 СТ РК 1073-2025) и к паре (Blen, Klen) профиля (QW-R1-F05: раундовые ключи Qalqan для разных Blen совпадают префиксом).
- Klen = 256 бит для обоих профилей.
- Реализация MUST проверять попарное различие K_e, K_m, K_m′ (T-PROP-05, T-NEG-10). Совпадение K_m = K_m′ делает EMAC уязвимым (СТ РК ISO/IEC 9797-1, примечания к §7.3).
- Использование развёртывания ключа Qalqan как KDF MUST NOT допускаться (гипотеза F04b).
- **BLOCKED (BR-05):** допустимость KDF-производных ключей для L3/L4 по §5.5.7/§5.6.7.
- Метки — PENDING (G0).

## 8. Шифрование и аутентификация пакетов

### 8.1 Подготовка

1. P — IP-пакет из TUN (возможно пустой — keepalive).
2. P′ = P ‖ 0x00^k, где k вычисляется политикой дополнения (по умолчанию — как `calculatePaddingSize`, `device/send.go:419–432`, кратность 16). Дополнение служит только сокрытию длины; криптографической роли не играет. Политика — TBD.
3. Счётчик c = атомарное приращение счётчика пары (как `send.go:356`); при c ≥ `RejectAfterMessages` профиля — пакет MUST NOT отправляться.
4. H = §4.4 байты 0..15.

### 8.2 Шифрование (CTR, ISO/IEC 10116 §10, j = Blen)

Блок счётчика CB(c, i) — массив из Blen/8 байт во внутреннем порядке Qalqan (байт 0 — младший при сложениях §6.3 СТ РК 4009-2025):

| Байты | Blen = 256 (профиль 0x01) | Blen = 128 (профиль 0x02) |
| --- | --- | --- |
| 0–3 | uint32 LE: номер блока i | uint32 LE: i |
| 4–7 | 0x00 | 0x00 |
| 8–15 | uint64 LE: счётчик пакета c | uint64 LE: c |
| 16–31 | 0x00 | — |

```
KS_i = Qalqan_E(K_e, CB(c, i)),   i = 0, 1, …, ⌈L/(Blen/8)⌉ − 1
C    = P′ ⊕ (KS_0 ‖ KS_1 ‖ …)[0 : L]
```

Требования: i < 2^32 (фактически i < 2^12 при L ≤ 65 535, Blen=128); для уникальности достаточно уникальности c на ключ K_e. **R2:** инъективность (c, i) ↦ CB(c, i) доказана аналитически (`QAZWIRE_SECURITY_BOUNDS_R2.md` §3.1: отображение имеет левый обратный); длина пакета MUST проверяться (L ≤ 65 519) до CTR и MAC. CB(c, i) = CB(c, 0) + i в целочисленной интерпретации little-endian — это CTR с начальным значением SV = CB(c, 0).
**PENDING:** соответствие порядка битов/байтов строкам ISO/IEC 10116 (там целочисленная интерпретация битовых строк). Для QazWire нормативным является указанное здесь байтовое представление; эквивалентность нотации 10116 подлежит подтверждению.

### 8.3 Имитовставка

Вход MAC: **M = H ‖ C** (H — 16 байт фиксированной длины, поэтому кодирование однозначно; счётчик и профиль входят в H и тем самым аутентифицируются — исправление дефекта механизма 5 СТ РК ISO/IEC 19772-2013, QW-R1-F03).

Профиль 0x01 — EMAC (СТ РК ISO/IEC 9797-1, алгоритм MAC 2), n = 256:
```
M* = M ‖ 0x80 ‖ 0x00^z, z ≥ 0 — минимальное, чтобы len(M*) было кратно 32 (метод дополнения 2)
X_1 … X_q — 32-байтовые блоки M*
Y_0 = 0^256;  Y_j = Qalqan_E(K_m, X_j ⊕ Y_{j−1}), j = 1..q
T = Qalqan_E(K_m′, Y_q)                          -- преобразование результата 2; без усечения (t = 256)
```

Профиль 0x02 — CMAC (алгоритм MAC 5, метод дополнения 4, метод установления ключей маски 2 с многочленом p₁₂₈), ключ K_m, t = 128.

**R2:** значения e_{K}(0^n) на ключах K_m, K_m′ (контрольные значения ключа) MUST NOT вычисляться для внешнего использования, публиковаться или храниться (примечания к §7.3 СТ РК ISO/IEC 9797-1: подделка XOR). Нормативная применимость любых режимов на Qalqan — BLOCKED (BR-10: §5 10116/9797-1/19772 требуют шифр из ISO/IEC 18033-3).

**PENDING:** соответствие «бит 1, затем нули» байту 0x80 при принятом порядке битов Qalqan — подтвердить совместно с §8.2.

### 8.4 Выход

`packet = H ‖ C ‖ T`.

### 8.5 Приём

1. len(packet) ≥ 16 + t/8, иначе — отбросить.
2. Байт 0 = 0x14, байт 1 = профиль устройства, байты 2–3 = 0; иначе — отбросить.
3. Поиск пары по receiver index; пара не просрочена (`RejectAfterTime`); иначе — отбросить.
4. c = uint64 LE из H[8:16]; если c ≥ `RejectAfterMessages` или c заведомо старше окна повторов — отбросить **без обновления окна** (предварительная проверка снижает DoS-стоимость, T14).
5. T′ = MAC(H ‖ C); сравнение T′ и T в постоянном времени по полной длине; при несовпадении — отбросить; открытый текст не формируется.
6. P′ = CTR-расшифрование C.
7. `ValidateCounter(c, RejectAfterMessages)` (окно RFC 6479, `replay/replay.go:37–62`) — **после** аутентификации, как `receive.go:453`; при отказе — отбросить.
8. Подтверждение пары `next` (как `ReceivedWithKeypair`, `noise-protocol.go:710–727`), обновление endpoint; усечение дополнения по длине из IP-заголовка и проверка адреса источника по allowed-IPs пира (cryptokey routing, как `receive.go:471–503`) — MUST сохраняться; затем доставка в TUN.

## 9. Обработка ошибок

| Ситуация | Поведение |
| --- | --- |
| Любая ошибка разбора/аутентификации | Тихое отбрасывание; ответных сообщений об ошибке нет; различимых по времени путей нет (кроме отказа по публичным полям) |
| Ошибка провайдера в `Seal` | Пакет не отправляется; счётчик ошибок; при повторении N раз (TBD) — сброс пары и новый handshake |
| Сбой самотеста | Устройство не создаётся; процесс завершается с кодом ошибки |
| Паника в провайдере | Считается дефектом; процесс MUST завершаться (fail-closed), а не продолжать с неопределённым состоянием |
| Журналирование | Только события и счётчики; MUST NOT содержать ключи, открытый текст, теги, полные заголовки; ограничение частоты. Защита журнала (§5.4.10–5.6.10 СТ РК 1073-2025) — TBD |

## 11. Защита от повторов и лимиты (R2)

**Значения ревизии R1 отменены:** для 0x02 они давали член CMAC ≈ 2^−32 и не учитывали проверки на приёме (`QAZWIRE_SECURITY_BOUNDS_R2.md` §0). Ниже — лимиты на **один ключ одного направления** при цели **T_A** (CA ≤ 2^−60, IA ≤ 2^−57, практика TLS/QUIC). Цель T_B (≤ 2^−72 на ключ) — альтернатива, выбор — решение владельца (G5). Математическое обоснование и допущения — `SECURITY_BOUNDS_R2` §3–§7.

| Параметр | WireGuard (`constants.go:15–22`) | 0x01 `QWX1-Q256EM` | 0x02 `QWX1-Q128CM` (T_A) |
| --- | --- | --- | --- |
| RekeyAfterMessages / RejectAfterMessages | 2^60 / 2^64 − 2^13 − 1 | 2^60 / 2^64 − 2^13 − 1 | 2^32 / 2^34 (страховочные) |
| RekeyAfterBlocks / RejectAfterBlocks (σ_e, блоки гаммы CTR, отправитель) | — | счётчик ведётся, порог не обязателен (σ_e ≤ 2^75 достижимо ≪ 2^92,5) | 2^33 / 2^34 |
| MaxTagBlocks (σ_tag, блоки входа MAC, отправитель) | — | не обязателен | 2^33 |
| MaxVerifyBlocks (σ_ver, блоки входа MAC по **всем** проверкам, получатель) | — | мониторинг | 2^33 → вывод ключа из употребления и новый handshake |
| MaxFailedVerifications (q_v) | — | порог мониторинга (TBD) | 2^33 |
| RekeyAfterTime / RejectAfterTime | 120 с / 180 с | 120 с / 180 с | 120 с / 180 с |
| Окно повторов (RFC 6479) | 8128 | 8128 | 8128 |
| Обоснование | Поточный шифр, Poly1305 | Обобщённые члены (1), (3), (2) пренебрежимы при любой достижимой нагрузке; итог определяется неизвестным Adv^prp Qalqan-256 (BLOCKED) | σ_e ≤ √(2^−60·2^129) = 2^34,5; (4σ_F² + 1)/2^128 ≤ 2^−58 → σ_F ≤ 2^34, делится поровну между отправителем и получателем |

Следствия:
- для 0x02 при скорости выше ≈ 9 Гбит/с в одном направлении ротация по объёму наступает раньше ротации по времени (`SECURITY_BOUNDS_R2` §7.4);
- лимит σ_ver даёт нарушителю рычаг принудительной ротации (BR-13).

Для толкования §3.4 СТ РК 1073-2025 (PENDING) для 0x02 потребовалось бы σ ≤ 2^32 (L2); L3/L4 при n = 128 недостижимы.

## 12. Ограничения безопасности (обязательный раздел ЭД)

1. **Не национальный протокол.** Handshake использует X25519, BLAKE2s, ChaCha20-Poly1305; Qalqan защищает только транспорт.
2. **Нет заявлений о соответствии** СТ РК 1073-2025 (ни L1, ни выше); по длинам handshake ограничен L2; стойкость не оценена.
3. **Qalqan не проанализирован независимо** в версии 2025 г. (BR-01); вероятность скрытых слабостей не оценена.
4. **Профилированная композиция** (MAC над H ‖ C) отличается от буквального механизма 5 СТ РК ISO/IEC 19772-2013 и требует нормативного согласования (BR-02).
5. **Побочные каналы:** до выполнения G2 реализация считается уязвимой к кэш-тайминговым атакам.
6. **Уничтожение ключей** в Go — best-effort.
7. **DoS:** проверка транспортных пакетов дороже, чем в WG.
8. **Анализ трафика:** длины и тайминги не скрываются сверх политики дополнения WG.
9. **Квантовый нарушитель:** X25519 не стоек; PSK — частичная мера для handshake.
10. **Компрометация хоста** — вне модели.
