# QazWire Experimental — модель угроз, R1

**Статус:** DRAFT / RESEARCH ONLY. Модель угроз описывает **экспериментальный** протокол QazWire v0.1 (`QAZWIRE_PROTOCOL_SPEC_R1.md`) в лабораторном применении на синтетическом трафике. Она не является ТЗ на ОКР по §6.5 СТ РК 1073-2025, но может служить его заготовкой.
**Дата:** 2026-11-02. Ссылки на код — `master` @ `b3bc704`.

## 1. Объект и границы

```
 [Приложение/IP-стек] ⇄ TUN ⇄ ┌─────────── QazWire device ───────────┐ ⇄ UDP ⇄ [Сеть: активный нарушитель] ⇄ UDP ⇄ [Пир]
                               │ handshake │ transport suite │ ключи  │
                               │ таймеры   │ replay-окно     │ UAPI   │
                               └──────────────────────────────────────┘
                                       ▲ конфигурация (static key, PSK, peers)
                                       ▲ ОС: CSPRNG, планировщик, память, swap, core dump
```

| Граница | Внутри | Снаружи / допущение |
| --- | --- | --- |
| B1 Криптографический модуль (логически) | Профиль, handshake, KDF, транспортный AE, replay, уничтожение ключей | ОС, Go runtime, GC |
| B2 Хост | Процесс QazWire | Компрометация хоста (root, отладчик, DMA) — **вне модели**: гарантии теряются |
| B3 Сеть | — | Полностью контролируется нарушителем (Dolev–Yao + вычислительные ограничения) |
| B4 Конфигурация | Static-ключ, PSK, список пиров | Защищённый канал доставки конфигурации — допущение (GAP для L3/L4) |
| B5 Цепочка поставки | Исходный код, зависимости, тулчейн | SBOM и проверка хешей — требование, не допущение |

## 2. Активы

| ID | Актив | Свойства |
| --- | --- | --- |
| A1 | Пользовательский трафик (синтетический) | Конфиденциальность, целостность, подлинность источника, защита от повторов |
| A2 | Сеансовые ключи K_e, K_m, K_m′ по направлениям | Секретность, однократность использования в рамках профиля, своевременное уничтожение |
| A3 | Static-ключи X25519, PSK | Секретность; привязка к протоколу QazWire и профилю |

| A5 | Идентичность пира (static public key) | Скрытие идентичности от пассивного наблюдателя (как в WG) |
| A6 | Доступность туннеля | Устойчивость к DoS в пределах свойств WG |
| A7 | Целостность реализации | Отсутствие ошибок/НДВ, корректность KAT |

## 3. Нарушители

| ID | Нарушитель | Возможности | Соотнесение с §4.3 СТ РК 1073-2025 |
| --- | --- | --- | --- |
| N1 | Пассивный сетевой | Запись всего трафика, анализ длин/времени | Любой уровень |
| N2 | Активный сетевой (MITM) | Перехват, изменение, повтор, переупорядочивание, внедрение, отражение пакетов; выбор времени | Любой уровень; бюджет — по уровню |
| N3 | Криптоаналитик с большим бюджетом | Предвычисления, большие объёмы памяти, атаки §4.5 | L3/L4 (бюджет до 10^9…10^12 МРП) |
| N4 | Локальный непривилегированный сосед (co-tenant) | Измерение кэша/времени на том же CPU | Реализационный |
| N5 | Злонамеренный/скомпрометированный пир | Знает свои ключи; пытается выдать себя за другого (UKS/KCI) | Любой |
| N6 | Компрометация долговременных ключей в будущем | Получает static и/или PSK после сеанса | Прямая секретность |
| N7 | Поставщик/цепочка поставки | Модификация зависимостей/бинарника | §5.1.5, §5.1.7 |

Вне модели: полная компрометация хоста (B2), физические атаки по питанию/ЭМИ (могут быть добавлены по §5.1.6), квантовый нарушитель (не рассматривается в v0.1; PSK даёт частичную защиту handshake).

## 4. Анализ угроз

Формат: угроза → механизм WireGuard (как сейчас) → влияние изменений QazWire → требования спецификации → остаточный риск → статус.

### T1. MITM (N2)
- **WG:** взаимная аутентификация через static-DH (es, ss, se) и PSK, транскрипт h как AAD (`noise-protocol.go:310`, `:325`, `:504`), поиск пира по расшифрованному static (`:374`). Доказано в моделях Lipp et al. / Dowling–Paterson.
- **QazWire:** handshake алгоритмически не меняется; меняются имя конструкции, prologue, метки → свойства переносятся **при условии** корректной доменной изоляции.
- **Требования:** профиль в имени конструкции (ck0) и в prologue (h0) — спец. §3; отдельные static-ключи.
- **Остаток:** зависит от стойкости X25519/BLAKE2s/ChaChaPoly (не национальные). **Статус:** сохраняется, требуется повторная формальная проверка модели (BR-09).

### T2. Повтор (replay) (N2)
- **WG:** транспорт — окно RFC 6479 на 8128 значений, проверка после аутентификации (`receive.go:449–455`, `replay/replay.go:37–62`); handshake — монотонный TAI64N (`noise-protocol.go:405–417`).
- **QazWire:** счётчик должен входить в MAC (в WG — через nonce AEAD). Если счётчик не покрыт MAC, нарушитель может переписать его и обойти окно → **критично** (QW-R1-F03).
- **Требования:** MAC над всем заголовком; окно обновляется только после успешной проверки MAC; лимит счётчика по профилю.
- **Остаток:** повтор initiation после перезапуска ответчика (теряется `lastTimestamp`) — известное свойство WG; приводит к лишнему handshake, но не к раскрытию данных. **Статус:** сохраняется при выполнении требований.

### T3. Downgrade (N2, N8)
- **WG:** нет согласования → нет downgrade.
- **QazWire:** появление профилей создаёт поверхность: (a) «откат» на стандартный WG, (b) переключение между профилями QazWire, (c) fallback при ошибке самотеста.
- **Требования:** профиль неизменяем на устройство; нет согласования в протоколе; профиль входит в ck0, h0, коды типов и метки KDF; любые несовпадения → тихий отказ; при сбое KAT/самотеста устройство не запускается; UAPI принимает только идентификатор QazWire.
- **Остаток:** ошибка оператора (запуск стандартного WG вместо QazWire) — организационная мера + явная индикация режима (§5.3.8). **Статус:** требует тестов T-XPROF-*.

### T4. Повтор nonce / перекрытие гаммы (N2/N3; §4.5 «перекрытие шифрующей гаммы»)
- **WG:** уникальность 64-битного счётчика на пару ключей; ChaCha20 — 96-битный nonce.
- **QazWire (CTR):** блок-счётчик формируется из (счётчик пакета, номер блока); поля номера блока (байты 0–3) и счётчика (байты 8–15) не пересекаются, поэтому блоки счётчика различны при номере блока < 2^32 и уникальном c (спецификация §8.2). Опасности: (1) повтор счётчика при гонке/переполнении; (2) одинаковые ключи в двух направлениях; (3) одинаковый ключ в двух профилях с разным Blen (раундовые ключи совпадают — QW-R1-F05); (4) клонирование ВМ со сохранённым состоянием сессии.
- **Требования:** атомарный счётчик (как `send.go:356`), жёсткий отказ при достижении лимита (`:357–358`); направленные независимые ключи; ключ привязан к (Blen, Klen, назначение); сеансовые ключи не сохраняются на диск.
- **Остаток:** клонирование работающей ВМ — вне модели (B2). **Статус:** PENDING тестов T-NONCE-*.

### T5. Компрометация ключей (N6)
- **WG:** прямая секретность за счёт эфемерного DH; PSK добавляет защиту от будущей компрометации static (и частично от квантового нарушителя); компрометация static позволяет выдавать себя за владельца **после** компрометации.
- **QazWire:** свойства handshake те же. Новое: (a) раундовые ключи Qalqan хранятся развёрнутыми; по гипотезе F04b их утечка эквивалентна утечке ключа; (b) объекты ключей не стираются (F09).
- **Требования:** `Destroy()` с подсчётом ссылок; никаких копий ключей вне объекта провайдера; минимизация времени жизни; запрет core dump/swap там, где возможно (`mlock`, `RLIMIT_CORE`) — best-effort.
- **Статус:** прямая секретность **ослаблена реализационно** (как и в WG, но с большей площадью из-за развёрнутых ключей) → BR-07.

### T6. Unknown key-share (N5)
- **WG:** обе static-идентичности входят в транскрипт (static ответчика — в h0 через `mixHash(remoteStatic)` `noise-protocol.go:287`; static инициатора — зашифрован и хеширован `:311`); доказано отсутствие mis-binding в CryptoVerif-анализе.
- **QazWire:** без изменений при сохранении шаблона. Транспортные ключи выводятся из ck, связанного с обеими идентичностями.
- **Статус:** сохраняется (повторить символьную проверку).

### T7. Reflection (N2)
- **WG:** ключ отправки ≠ ключ приёма (`noise-protocol.go:634–647`); отражённый пакет не проходит `Open`.
- **QazWire:** **обязательно** выводить K_e/K_m отдельно для каждого направления из разных выходов KDF2; запрещено выводить оба направления из одного 32-байтового ключа без метки направления.
- **Статус:** сохраняется при выполнении требования (T-NEG-REFL).

### T8. Обход аутентификации (N2)
- Риски QazWire: (a) расшифрование до проверки MAC (in-place буфер `receive.go:255` → открытый текст в буфере при ошибке); (b) неконстантное сравнение тега; (c) усечение тега/«совместимый» короткий тег; (d) принятие пакета с ненулевыми резервными байтами/неизвестным профилем; (e) использование `Open`, возвращающего частичный открытый текст.
- **Требования:** MAC-проверка полного тега постоянного времени **до** CTR; при ошибке — буфер не содержит открытого текста; без усечения; строгий разбор заголовка.
- **Статус:** PENDING тестов T-NEG-*.

### T9. Нарушение прямой секретности
См. T5. Дополнительно: `Handshake.Clear()` (`noise-protocol.go:246–253`) обнуляет эфемерные данные, но не PSK и не предвычисленный static-static; `precomputedStaticStatic` живёт всё время существования пира — как в WG. **Статус:** сохраняется на уровне протокола, ослаблено на уровне реализации Go.

### T10. Ошибки разделения криптографических доменов
- Риски: (a) смена только `WGIdentifier` → ck совпадает с WG (QW-R1-F10); (b) одинаковые метки MAC1/cookie → ответы на чужие handshake; (c) один static-ключ в WG и QazWire; (d) один и тот же ключ Qalqan для CTR и EMAC (нарушение §5.1.4 и классическая уязвимость CBC-MAC + CTR с общим ключом); (e) один ключ с разными Blen (F05); (f) ключи K_m и K_m′ EMAC равны (подделка XOR по 9797-1, прим. к §7.3).
- **Требования:** изменить имя конструкции; метки на профиль; HKDF-Expand с уникальными метками для каждого ключа; самотест «ключи попарно различны».
- **Статус:** BLOCKING для реализации до прохождения T-DOM-*.

### T11. Обработка повреждённых пакетов
- Риски: целочисленные переполнения при вычислении длин (`calculatePaddingSize` `send.go:419–432`), короткие пакеты, частичный последний блок CTR, дополнение EMAC, пустой открытый текст (keepalive), неизвестные типы, паника в провайдере → DoS.
- **Требования:** длины проверяются до любой криптографии; провайдер не паникует (ошибка → drop); фаззинг парсеров и провайдера.
- **Статус:** PENDING (T-FUZZ-*).

### T12. Утечки по времени выполнения (N4)
- **WG:** ChaCha20/Poly1305/X25519 в `x/crypto` — без зависящих от секрета ветвлений и обращений к памяти.
- **QazWire:** S-блок Qalqan — таблица 256 байт, индексируемая секретом; в развёртывании ключа — индексация байтами ключа (Прил. Б СТ РК 4009-2025). Прямой перенос даёт кэш-тайминговую утечку → BR-03. Сложение mod 2^Blen должно реализовываться фиксированной цепочкой переносов. Сравнение тега — `subtle.ConstantTimeCompare`.
- Ранний отказ по публичным полям (тип, длина, индекс) допустим.
- **Статус:** BLOCKED для не-лабораторного применения.

### T13. Нарушения при обновлении ключей
- **WG:** previous/current/next, подтверждение `next` первым принятым пакетом (`noise-protocol.go:710–727`), лимиты по времени/сообщениям, стирание через 3×RejectAfterTime.
- **QazWire:** (a) гонка `Destroy()` со шифрованием в рабочих потоках (QW-R1-F09) — **отправка пакетов под обнулёнными раундовыми ключами**; (b) лимиты сообщений для 128-битного блока (F07); (c) пакеты старой пары после уничтожения должны отбрасываться, а не расшифровываться «пустым» ключом.
- **Требования:** подсчёт ссылок; флаг «уничтожен» проверяется атомарно в `Seal/Open`; после уничтожения — только ошибка; тесты гонок (`-race`) и стресс-ротации.
- **Статус:** PENDING (T-REKEY-*).

### T14. DoS через дорогую проверку транспорта (дополнительно)
- Индекс получателя виден на проводе; любой может отправить поток мусорных транспортных пакетов, каждый из которых требует вычисления EMAC (≈ len/32 вызовов Qalqan-256). Cookie WG защищает только handshake.
- **Меры (TBD):** лимиты скорости по источнику до криптографии, раннее отбрасывание по окну повторов *без* обновления окна (предварительная проверка «счётчик слишком стар»), мониторинг.
- **Статус:** PENDING (T-PERF-DoS).

## 5. Гарантии WireGuard: сохраняются / теряются / требуют нового доказательства

| Гарантия WG | В QazWire v0.1 | Обоснование |
| --- | --- | --- |
| Взаимная аутентификация, KCI-устойчивость, отсутствие mis-binding | **Сохраняется (переносится)** | Handshake алгоритмически не изменён; требуется перепроверка символьной модели с новыми константами |
| Скрытие идентичности инициатора | Сохраняется | Static шифруется ChaCha20-Poly1305 как в WG |
| Прямая секретность (протокольная) | Сохраняется | Эфемерный DH без изменений |
| Прямая секретность (реализационная) | **Ослаблена** | Развёрнутые раундовые ключи, отсутствие гарантированного затирания в Go (F04b, F09) |
| Конфиденциальность и целостность транспорта (ACCE) | **Требует нового доказательства** | ChaCha20-Poly1305 заменён на CTR+EMAC (N2); нужна стойкость Qalqan-256 как PRP и адаптация доказательства (Lipp et al. предполагают AEAD IND-CPA+INT-CTXT) |
| Защита от повторов | Сохраняется при выполнении требований | Счётчик обязан входить в MAC |
| Отсутствие downgrade | **Требует нового обоснования** | Появились профили; изоляция обязательна |
| Реализация без побочных каналов | **Теряется** до решения BR-03 | Табличный S-блок |
| Проверенные реализации примитивов | **Теряется** | Новый, непроверенный код Qalqan |
| Производительность и DoS-устойчивость транспорта | **Ухудшается** | Два прохода блочного шифра; T14 |
| Совместимость с WG | **Теряется намеренно** | Новый протокол |
| Простота (отсутствие криптоагильности) | Частично сохраняется | Профиль фиксирован на устройство, без согласования |

## 6. Блокирующие архитектурные риски

См. регистр BR-01…BR-09 в `QAZWIRE_CRYPTO_AUDIT_R1.md` §9. Для модели угроз критичны: **BR-01** (стойкость Qalqan), **BR-03** (тайминг), **BR-07/F09** (уничтожение ключей и гонка), **BR-09** (новое доказательство транспорта), а также требования доменной изоляции T10 — без них реализация M2 не начинается.
